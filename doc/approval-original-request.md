# Approval original-request snapshots

Board approval payloads may include an `originalRequest` object so the decision surface can show the source request separately from the recommendation, rationale, and proposed outbound draft.

```json
{
  "originalRequest": {
    "text": "Exact source wording, including\nline breaks.",
    "source": {
      "kind": "external",
      "channel": "email",
      "sender": "Known sender, when available",
      "sentAt": "2026-10-03T12:00:00.000Z",
      "reference": "provider message or thread reference",
      "snapshotOrigin": "requester"
    }
  }
}
```

`text` is an immutable plain-text snapshot. UI clients render it as escaped text, never Markdown or HTML. They must not derive it from `summary`, `reasoning`, `recommendedAction`, an issue description, or an outgoing email `body`.

For an existing Paperclip issue comment, set `source.kind` to `paperclip_comment` and provide its real `commentId`. The approval create/resubmit route retrieves the non-deleted comment inside the approval company and replaces the text and provenance with a server snapshot (`snapshotOrigin: "server"`). A missing or cross-company comment is rejected. For external sources, the requester supplies the exact retrieved text and any actually known provenance; Paperclip marks the snapshot as requester-provided (`snapshotOrigin: "requester"`) and does not claim independent verification.

Resubmitting decision fields without an `originalRequest` preserves the prior snapshot. Supplying a new `originalRequest` is an explicit source change and is recorded in approval activity. Existing approvals are not backfilled; absent snapshots render a clear missing-source state.

Approval detail, shared approval cards, and both inbox presentations place the original request between Recommendation and Why. Inbox decisions follow the shared decision summary. Compact summaries (the card and the inbox row) show the first lines of a long request, more than 480 characters or more than 16 lines, behind a **Show full request (N characters)** button; the retained text is never shortened. The approval detail page shows the whole request. No surface puts the request, or the proposed reply, in a box with its own scrollbar: the text is either shown whole or behind that announced preview. The request and the draft reply are set in the interface's text face, not in monospace, on every surface and under **Full request**; every character, space, and line break is kept. The provenance line under **Original request** is described in "Who asked, and when" below.

`originalRequest` is optional, so an approval can have no source: an older record, or a request the agent raised by itself. The interface does not guess which. The card and the inbox row add "No original request attached" to their header line and show no empty source section. The approval detail page keeps the **Original request** section and states that no original request was attached. A request that also has no pros and no risks says so once in a single line, **No pros or risks were recorded.**, instead of empty fields. The line states what is missing and nothing about why: the interface cannot tell an old request from a new one that left the fields out.

### Who asked, and when

The line under **Original request** answers who sent the request and when, in words the board can read. Its parts are separated by `·` and each is left out when it is not known:

- **Channel**, for an external source (for example `Email`).
- **Sender.** For a Paperclip comment the server stores the author's user id or agent id, not a name. The interface never prints that id. An agent id is a UUID: it is shown as the agent's name when the company's loaded agent list holds it, and is left out when it does not (the agent may have been removed, and its comment is not called the board's). Any other id is a board user's: the sender is shown as **Board**, the name the discussion list on the detail page gives every non-agent author. Users are not named individually, because the interface has no user names to resolve an id against; a user whose id happens to be a UUID is left out like an unknown agent. For an external source the sender the requesting agent supplied is shown as written (`Sam Example <sam@example.test>`, and also an address such as `local-pickup@shop.example`), unless it is an id: a UUID, or a bare local user id (`local-` followed only by letters, digits, `-`, or `_`, such as `local-board`). An id is resolved in the same way (`local-board` is **Board**) or left out.
- **Time sent**, in the reader's locale, with a medium date and the time to the minute (`Oct 7, 2026, 1:23 AM`). A value that is not a date is left out.
- **Reference**, for a source that is not linked to a comment (for example a thread reference).
- **How the text got here.** **Saved from the original comment** for a snapshot the server took from a Paperclip comment; **Quoted by the requesting agent, not verified** for an external source the requester supplied. Paperclip has not checked that an external source says what the agent quotes.
- **View comment**, a link to the Paperclip comment the request came from.

The approval detail page shows the same line above the decision buttons and in **Full request**. The raw payload inside **Full request** is a technical view and still holds the stored ids.

## Decision surfaces

One shared decision summary is used by the approval card, both inbox presentations, and the approval detail page. It shows what the board is about to approve:

- A Board approval's `summary` leads the brief under a **Summary** label, with the same preview as the other text fields. Agents are told to send a summary and may put the cost in it, so it is not left to **Full request**. It is not repeated when the surface already shows the same words (compared without case, markup, and extra spaces): as the recommendation; as the rationale, which is the summary itself when the request gives no other; or as the title, when the request has no `title` and the summary is short enough to be shown whole as one (120 characters). Hire and strategy approvals have their own summaries and show no such field.
- An email-reply approval (an outgoing `body` with `subject`, `recipient`, or `channel`) shows the draft under a **Draft reply** label, after the decision brief and before the decision buttons. The draft is never used as the original request.
- The draft's header rows are **Via**, **From**, **To**, and **Subject**, each shown only when the request carries it. **Via** is the payload's `channel`, a free-text description of how the reply goes out (for example `email from info@`); it is not a sender address and is not labelled as one. **From** is shown only when the payload has a `from` string. **To** is `recipient`. **Full request** uses the same rows.
- Under the draft, while the approval is `pending`, one line written by the interface says what approval sets in motion: **If approved, the requester is told to send this reply to _recipient_.** The server wakes the requesting agent with the decision; Paperclip sends no email itself, and the line does not say the reply is sent. The line appears only when the payload has a `recipient`, the approval was requested by an agent (nobody else is woken), and the request has no `nextActionOnApproval` of its own.
- The draft body is shown whole when it is at most 1,500 characters (blank space at its end is not counted). A longer body is shown whole on the approval detail page. The card and the inbox row show about its first 1,500 characters, cut at a line or word boundary. The body box holds only the email's own characters: nothing is added to mark the cut, because an ellipsis there could be read as part of the email. Directly under the box a muted line says **The reply continues: N more characters.**, above a **Show full reply (N characters)** button. The body is never clamped to a number of lines.
- `nextActionOnApproval` appears as **If approved**. It is the requesting agent's own statement and takes the place of the line above.
- Each pro and each risk sits beside one bullet. One leading list marker of its own (`- `, `* `, `• `, `1. `, `1) `) is dropped, so a numbered risk does not show a bullet and a number. An item that is itself a list of several lines keeps its markers.

The summary has two modes:

- **Compact** (card and inbox row). Recommendation, rationale, and next action show their first lines (about three lines, or 180 characters for the recommendation and 220 for the others) with **Show more**. Line breaks are kept, also when nothing is hidden. Pros and risks beyond the first two, a draft of more than 1,500 characters, and a long original request expand in place.
- **Full** (approval detail page). Nothing is shortened and nothing needs expanding: the whole recommendation, rationale, next action, every pro and risk, the whole draft, and the whole original request are shown above the decision buttons. A Board approval states **Not supplied.** for a recommendation or rationale its request leaves empty; empty pros and risks are stated as on the card. The page heading carries the whole title.

The detail page uses the full summary for Board, hire, and strategy approvals. A budget override, which is resolved in Costs and has no decision buttons here, shows its scope, window, metric, limit, observed amount, and guidance instead. **Full request** below the decision buttons repeats the request with its technical fields; nothing in it is height-capped either, apart from the raw payload. It uses the same labels as the summary above it: **Recommendation**, **If approved**, and **Draft reply**.

The detail page never shows an id, or a piece of one, as a name. The last breadcrumb is the request's subject, cut to about 40 characters at a word boundary, or the kind of request (for example **Board Approval**) when it has no subject. A requester or a comment author whose name is not in the company's loaded agent list is shown as **An agent**; a comment written by a user is shown as **Board**. A linked task is named by its identifier and title, or by its title alone when it has no identifier. The **Request ID** line inside **Full request** stays: it is labelled as an id.

The detail page leads back to the queue. A **Back to the queue** link stands above the request, and the **Approvals** breadcrumb has the same target. Both go to the view the request was opened from, at that request's card: **View details** in the queue hands the page the queue's address (the tab, the kind filter, and the sort), and the way back adds `#approval-<id>` to it. The queue then opens that card, pages far enough to show it, and moves focus to it; when the request is no longer listed there, it opens no card and says so (see "Links to one request" below). A page that was not opened from the queue, for example from the inbox, leads back to `/approvals/pending#approval-<id>`. The page has no previous or next request: it approves at once, and working the queue from there would bypass the five-second hold.

Hire and strategy approvals carry no recommendation, pros, or risks, so they have their own summary on the card, in the inbox row, and on the detail page:

- A `hire_agent` approval is headed by the agent's name. It shows the role, job title, manager, adapter and model, monthly budget, the described work, and the skills. A manager is shown by name, never by id. While the decision is open, it states what each decision does: approval activates the agent the request names (or creates one when it names none) and sets the monthly budget when one is given; rejection terminates the named agent. If the request names an existing agent other than the one being hired, the summary says so instead. Only the model name is read from the adapter configuration.
- An `approve_ceo_strategy` approval shows the plan under a **Plan** label with its line breaks, numbering, bullets, and indentation. A long plan shows its first lines and expands in place; the detail page shows it in full. A recommendation, pros, risks, and next action are shown when the request carries them. A request with no plan field shows its rationale as the plan.

On the detail page a hire also lists every skill.

Agent-written text on these summaries is shown as plain text, never rendered as Markdown. Only markup is removed: heading marks, `**bold**` pairs, backtick pairs, rule lines, and link syntax. A link becomes `label (target)`. An embedded image cannot be shown, so it leaves a trace: `[image: alternative text] (target)`, or `[image] (target)` when it has no alternative text; an image that is itself a link becomes `[image: alternative text] (image target) (link target)`. A `**` pair is removed only where it is markup: the opening pair does not follow a letter, digit, underscore, slash, or asterisk and is not followed by a slash, and the closing pair is not followed by a letter, digit, underscore, or asterisk. `2**10 to 2**12`, `src/**/a.ts and test/**/b.ts`, and a glob that starts or ends a path (`**/dist/**`, also inside backticks, which are removed) are therefore shown as written. The price is that bold text which begins with a slash, such as `**/approve**`, keeps its asterisks. A `-` or `*` list marker is shown as a bullet. Everything else is kept as written: underscores, tildes, single asterisks, a leading `>` or `+`, identifiers, paths, line breaks, numbering, and bullets. One-line titles and subjects use the same conversion with line breaks folded into spaces, cut at a word boundary where a surface has a length limit.

A cut never falls inside one character as the reader sees it. Where the text has no space near the limit (Thai, Chinese, or Japanese text, a long address), the cut moves back to the start of the character it would split: a letter with its accent or tone mark, a flag, an emoji joined from several, a keycap, an emoji with a skin tone. This holds for one-line excerpts, for the first-lines preview of a long text, and for the preview of a long draft reply. It uses the browser's own text segmentation (`Intl.Segmenter`); a browser without it keeps only the two halves of a surrogate pair together, as before. A single character stored as more than 64 UTF-16 code units (dozens of stacked marks) is cut at the limit like any unbroken run.

#### Cost on hostile text

The server puts no length limit on these fields, so the conversion (`ui/src/lib/approval-readable-text.ts`) is written so that its cost grows in step with the length of the text, whatever the text holds, and so that no text makes it throw. The cost per character is not the same for every text. Measured with `node` v26.8.1, best of several runs, per megabyte: plain prose about 5 ms, prose with links, an image, bold, and lists about 32 ms, the slowest link shape about 45 to 60 ms, and text made of very many short lines about 100 to 260 ms (see below).

- Links and images are found in one pass over the text, not with a regular expression. The earlier patterns retried a 2,000-character target from every `[`. Measured with `node` v26.8.1 on 1 MB (1,048,576 characters), best of three runs, before and after: `[a](` repeated 3,113 ms and 2.8 ms; `[` repeated 2,074 ms and 2.8 ms; `![` repeated 2,047 ms and 2.8 ms; `![a](` repeated 5,112 ms and 2.5 ms; `[a](` repeated with one `)` at the very end 3,111 ms and 16.6 ms; `[![a](b)](` repeated 1,237 ms and 59.4 ms. 1 MB of ordinary prose with links, images, and bold takes 10 ms and 16.2 ms. The single pass finds the same links as the patterns did, up to the same limits (a label of 300 characters, a target of 2,000, both on one line); this was checked on 400,000 random strings.
- A rule line (`---`, `***`, `___`, with or without spaces between the marks) is recognised by a loop over its characters, not by a regular expression. The earlier pattern overflowed the regular expression stack on one line of about 3.36 million marks (also when words followed them) and threw; the error replaced the whole page, on the queue, in the inbox, and on the detail page, so the request could not be rejected from any screen. One line of 8 MB of `-`, `_`, `* `, or `-` followed by a word now converts in 31 to 39 ms. The loop gives the same answer as the pattern on every line of up to six characters built from a space, the three marks, and a letter (19,530 lines, checked in the tests).
- The four per-line steps (heading mark, list marker, bold pair, backtick pair) run only on a line that holds the character they look for, and not at all on an empty line. Text of very many short lines paid for all four on every line before. Measured the same way on 1 MB, before and after: a run of line breaks 735 ms and 107 ms; `x` and a line break repeated 380 ms and 96 ms; a run of carriage returns 786 ms and 185 ms; `- x` and a line break repeated (every line a list item, so every line is rewritten) 376 ms and 262 ms. On 5 MB: line breaks 4,056 ms and 627 ms; `x` lines 1,906 ms and 507 ms; `- x` lines 1,974 ms and 1,443 ms. The cost stays in step with the length, and the conversion is run once per payload (last point below), but a hostile text of several megabytes of list items still holds the page for a second or more when its card is first drawn. The checks change no output: on 300,000 generated strings the result equals that of the earlier code with only the `**` rule above changed.
- A one-line excerpt (a title, a breadcrumb, the one line of a closed queue row) converts only the start of its text: four times its length plus 2,400 characters, cut between words. A text that was cut this way always ends in an ellipsis.
- A `summary` longer than 20,000 characters is not converted and compared with the recommendation, the rationale, and the title; it is shown. The one exception costs nothing: when it is character for character the text already shown as the recommendation or as the rationale (which is the summary itself when the request gives no other rationale), it is not shown a second time. Shorter summaries are compared whole, never by their first characters, so a summary that only begins like the recommendation is not dropped.
- The summary, a hire's facts, a strategy's plan, the pros and risks, the card's title, and a closed row's one line are converted once per payload and kept, not converted again on every render.

The file imports nothing, so it can be timed directly: `node -e 'import("./ui/src/lib/approval-readable-text.ts").then(({ approvalReadableText }) => { const text = "[a](".repeat(262144); const start = performance.now(); approvalReadableText(text); console.log(performance.now() - start); })'`.

**Request changes** is offered only when the approval has a requesting agent to receive it.

The approval card, the approval detail page, and Board, hire, and strategy approvals in both inbox presentations use the same decision buttons:

- **Approve** sends at once in the inbox, on the detail page, and on a task page. On the Approvals page it is held for five seconds first, with **Undo** (see "The undo window after Approve" below). On every surface an outgoing email is never approved while part of it is cut. On the card and in the inbox row, while a long draft is cut, the button says so before it is pressed: it reads **Read full reply to approve** in the place of **Approve**, and its accessible name is the same words followed by the request's title. That first press (a click or `Shift+A`) sends nothing. It opens the whole draft, moves keyboard focus to the draft, scrolls it into view, and shows **Read the full reply, then approve.** beside the buttons. The button then reads **Approve**, and the next press sends. When the board has already opened the draft with **Show full reply**, **Approve** sends at once; cutting the draft again with **Show less** holds it back again and brings **Read full reply to approve** back. While a revision is waiting to be confirmed (see "Requests that change while open"), the button keeps reading **Approve**: that press deals with the revision and does not open the draft. In short, **Approve** sends only while the whole draft is on the page. The detail page always shows the whole draft, so **Approve** sends at once there.
- **Add a note** attaches an optional `decisionNote`. A note typed before **Approve** was held back is kept and sent with the decision.
- **Request changes** is available while the approval is `pending` and requires a `decisionNote`, so the requester knows what to revise.
- **Reject** asks for confirmation and accepts an optional reason as the `decisionNote`.
- **Request changes** and **Reject** are never held back by a cut draft.

The note, change-request, and reject panels work from the keyboard:

- Opening a panel puts the cursor in its field and scrolls the decision controls into view, so the field and the buttons that send it are on screen together. `Escape` or **Cancel** closes the panel, discards what was typed, and returns focus to the button that opened it.
- `Ctrl+Enter` or `Cmd+Enter` in the field sends the open confirmation: the change request (only when a note is written) or the rejection. There is no such key for **Approve**.
- The panel is a group named by its prompt. **Reject this request?** is also read out with the reason field.
- In the inbox with keyboard shortcuts enabled, `Enter` opens the selected row. On a focused button inside a row (**Approve**, **Reject request**, **Send request**, **Show more**, **I have reviewed it**) it presses that button and does not open the row, so a typed note is not lost. `J`, `K`, and the up and down arrows take focus off such a button, so the next `Enter` opens the row they moved to. A mouse click can leave focus on a row button without a visible ring; when the pointer has since moved to another row, `Enter` opens that hovered row and does not press the button left in focus. With the pointer on the same row as the focused button, or not moved since the last `J`/`K`, the button is pressed. Its cost: a reader who reaches a button with `Tab` while the pointer, moved since the last `J`/`K`, rests on another row gets that row opened. A held `Enter` acts once: its repeats do nothing, so one press cannot both approve a request and open a page. From a tab or a toolbar button, `Enter` opens the selected row as before.

Feedback for a decision stays with the request it belongs to:

- While a decision is being sent, only that request's buttons are disabled. The pressed button shows its busy label (**Approving...**, **Sending...**, **Rejecting...**) and the control is marked busy for assistive technology. Other cards and inbox rows stay usable, and a second decision for a request that is still sending is not sent. On the Approvals page an approval has no buttons while it is sent: its compact row reads **Approving...**.
- A decision that comes back as an error is reported on that request, directly above its buttons: **Error while approving: _message_** (or **rejecting**, **requesting changes**). In the inbox, on the detail page, and on a task page the line is an alert. On the Approvals page it is plain text, and **Approve** is described by it: that page announces each outcome once in its live region (below), and an alert on a card that is drawn again whenever it is closed or opened would speak an old failure each time. The typed note is kept. The error is removed when the board edits the note or sends the decision again. An inbox row with the plain **Approve** / **Reject** buttons shows the same line under them.
- The message that says why **Approve** was held back (**Read the full reply, then approve.**, **Confirm that you have reviewed the revised request, then approve.**) arrives in a polite status region that is on the page before it has any text. While empty the region is hidden from sight only, not removed, so the message is spoken when it appears.
- The error does not say the request is still undecided. The server stores a decision before it runs what follows from it (activating a hire, writing the activity log, waking the requester), so an error can come back for a decision that was stored. The Approvals page and the detail page therefore reload after an error and show the status the server holds; the request stays listed with its error even when it can no longer be decided. The inbox does not reload on an error.
- The Approvals page has one visually hidden live region that announces each outcome: **Approved: _title_**, **Rejected: _title_**, **Changes requested: _title_**, or **Error while approving _title_: _message_**. It also announces the start of a hold, **Approving in 5 seconds. Shift+Z undoes it. _title_** (**Undo is in its row.** when keyboard shortcuts are off; the title comes last because it can be long), an undo, **Not approved: _title_. Nothing was sent.** (followed by **Its status is now _status_: decided elsewhere.** when the request stopped being pending during the hold; the same words are said, without an Undo, when a held approval is taken back because its request was approved, rejected, or cancelled elsewhere), the end of a pause that used up its thirty seconds, **The pause is over: approving in _N_ seconds. Undo is in its row. _title_** (said once, not every second), a held approval taken back because its request was revised, **Not approved: _title_. The requester revised it before it was sent. Nothing was sent.**, or sent back for changes, **Not approved: _title_. It was sent back for changes before your approval was sent. Nothing was sent.**, a request decided elsewhere under the reader, **_Status_: _title_. Decided elsewhere.**, and a link to a request the tab does not list.
- The line at the top of the Approvals page is only for a failure to load the list. The line at the top of the inbox is for failures that do not belong to an approval row (join requests, archiving). On the detail page, a comment or delete failure is shown beside its own button.
- Approval cards on a task page still report a failed decision as a toast. The card there offers **Request changes** as well, under the same rules: only for a `pending` request with a requesting agent, and only with a note. It sends at once, and the toast reads **Changes requested**, or **Request for changes failed** with the server's message.

Board approvals decided on the Approvals page or in the inbox are decided in place. In the inbox an approved hire or strategy opens its confirmation page (`/approvals/<id>?resolved=approved`), but only when no other approval decision from the inbox is still on its way and no other approval row shows the error of a decision that failed; otherwise it settles in place like a Board approval, because leaving the inbox would drop the other row's outcome, or the error already on that row together with the note typed for it, and they would be shown nowhere. A row's own error does not hold back its own retry. Once the other row's error is gone (the decision was sent again, or its note was edited), the next approved hire or strategy opens its confirmation page again. So it does once the failed row itself is no longer on screen, because the tab hides a request someone else has decided, the search leaves it out, or the row was archived: no row shows the error then, and leaving drops nothing. The error is kept, and counts again if the row returns.

An inbox row shows the shared summary only for a request that is still open: `pending`, or sent back for changes. A request that was already approved, rejected, or cancelled when the inbox was opened is its title line with its status and the missing-source note; the title still links to the request's page. A request that was open in its row on this visit keeps its summary when it is decided, from the row or by someone else. The summary stays as it was drawn, with the line that says what approval sets in motion, and one line stands where the buttons were: **This request is approved.** (or **rejected**, **cancelled**). That line is as tall as one row of buttons, so nothing below the row moves up under the pointer when the decision lands. On the next visit to the inbox the row is its title line, and so it is when the row is drawn anew during the visit, for example after a search had hidden it. A row that shows a summary has more room under it, and in the streamlined inbox a line, so its buttons do not run into the next row's title. Two cases still make the row shorter when the decision lands: a note, change-request, or reject panel that was open closes, and on a narrow screen the buttons can take two lines where the outcome takes one.

The Approvals page lists the longest-waiting request first, marks requests that have waited seven days or more, shows linked tasks on each card, filters by kind, and has a search field (see "Search" below). With keyboard shortcuts enabled, `J`/`K` move to the next or previous request, open it, and put focus in it. `Shift+A`, `Shift+C`, and `Shift+X` approve, request changes, and reject for the open card, and only while focus is inside it: the card on load is open, but focus is on the page until `J`, `K`, a click, or `Tab` puts it in the card. `Shift+Z` takes back the approval held most recently, wherever focus is. A held-down key decides nothing. The line beside the sort control and the `?` cheatsheet (under **Approvals**) say the same.

The keys are compared without regard to case, together with the `Shift` key, so they work with Caps Lock on (the browser then reports `J` for a plain `j` and `a` for `Shift+A`). A plain letter without `Shift` never approves, rejects, or undoes, in either case, and `Shift+J` / `Shift+K` stay unused. The app-wide **new task** key is a plain `c`: a lower-case `c` that arrives with `Shift` down is `Shift+C` typed with Caps Lock on, and no longer opens the new-task dialog (`ui/src/hooks/useKeyboardShortcuts.ts`), on this page or any other.

### Approvals on the Decisions pages

The Decisions pages (`/decisions` and `/decisions/queues/:key`) list approvals among other items that wait for the board. Both routes are always registered; the sidebar links to them only when the experimental **Decisions** setting is on. Their rows show a title and a short excerpt, not the shared decision summary: no outgoing draft, no budget of a hire, no plan.

No approval is therefore decided on such a row, whatever its type: Board, hire, strategy, budget override, an approval whose type the feed does not give, or a type added later. The rule is by the item being an approval, not by a list of types. The row has no **Approve**, **Reject**, or **Request revision** button, collapsed or expanded, and no note field. It carries one link, **Review and decide**, to the approval's detail page, where the whole request sits above the decision buttons. Snooze, dismiss, the triage controls, and **Restore** on a snoozed row are unchanged.

The keyboard follows the same rule. On `/decisions`, `Enter` on a selected approval opens its page; it does not open the row as if the row could resolve it. The page's one-time opening of the topmost row that can be resolved in place skips approvals. The feed still marks every approval except a Board approval as resolvable in the row and lists three verbs for it; the interface ignores both for approvals.

A budget override (`budget_override_required`) was the last type decided on these rows, in one click. That is gone, because the decision did nothing: the approve route only changes the approval's status, while the budget is raised and the agent or project resumed only from Costs. The row said **Approval approved**, the item left the feed, and the stop stayed in force. The approval's detail page shows a budget stop by its scope and amounts, with no decision buttons, and sends the board to Costs.

### The queue on the Approvals page

The sidebar has an **Approvals** item directly under **Inbox**, in both sidebar layouts. It links to `/approvals` and is the current item (highlighted, with `aria-current="page"`) on **To decide**, on **All decisions**, and on an approval's own page. `/approvals` shows the queue itself, and the page then corrects the address to `/approvals/pending` in place, keeping a query string, a `#approval-<id>` target, and what the link carried. It is not a redirect: the Approvals page stays the same page across `/approvals`, `/approvals/pending`, and `/approvals/all`, so pressing the item on **All decisions** goes to **To decide** without losing the notes typed in the cards or the revisions on record. (Going from **All decisions** to **To decide** is a tab change like any other, and a tab change sends the approvals that are still held.) On **To decide** itself the item links to the address the reader is on, with its query (the kind filter and the sort) and its `#approval-<id>` target: pressing it there does nothing. It does not send a held approval early, remove its **Undo**, clear the filter, add a history entry, or scroll the queue. Its badge counts the company's `pending` approvals: the requests listed under **To decide**. Requests sent back for changes are not counted. The count is read from the same approvals list the Approvals page and the inbox load, so it adds no request of its own and follows live approval events. The mobile bottom bar has no such item; on a phone the queue is reached from the sidebar drawer.

The announcement card (see `doc/ANNOUNCEMENTS.md`) is not drawn on the Approvals pages: the queue, **All decisions**, and an approval's own page. It is fixed to the bottom-left corner and is wider than the sidebar, which is where the open request's **Approve** button comes to rest, and a click meant for **Approve** landed on the card's link and left the page. An announcement that is due appears on the next page the board opens.

The queue is built to be scanned and to keep the reader's place.

- **Compact rows.** Under **To decide** each request is a card that is either closed or open. A closed card is one compact row: kind, status, linked tasks, who asked, how long it has waited, the missing-source note, the title, and one line of what is asked (the recommendation of a Board approval, **What it will do** for a hire, the first line of a strategy's plan; nothing when the request carries none). The title and that line are cut to the row's width by the browser. The row's header is a button inside the heading that opens and closes the card, and its click area covers the title, the kind and status badges, and the one line of what is asked. Linked tasks stay links of their own, each at least 24 pixels tall. **View details**, in the open card, in a decided row, and in a row under **Waiting on the requester**, is 16 pixels tall; on a touch screen its tap area is 44 pixels tall and no wider than the link. No row is taller for it. The area ends before the next row, and the decision buttons are drawn above it. The line with the requester and the times, and a closed row's error, sit above the click area: the exact time shows on hover and the text can be selected, and a click there does not open or close the card.
- **Every row has a name.** The page moves focus to a card or a compact row after a decision, an undo, `J`/`K`, **Show N more**, and a link to one request. A card is a group named by its title, and its header button is described by the row's kind, status, requester, and waiting time, and by the error a closed row shows. A held row is named **Approval held: _title_** (the countdown is not part of the name), a decided row **_Status_: _title_**, and a row under **Waiting on the requester** **Revision requested: _title_**.
- **Nothing is decided from a closed row.** The summary, the draft, the note field, and the decision buttons are drawn only when a card is open, and `Shift+A`, `Shift+C`, and `Shift+X` do nothing on a closed card. A closed row still says when its decision is being sent, shows the error a decision came back with (two lines of it at most, so a long message does not push the card being read down the page; the whole message is on hover and in the opened card), says **Revised while this page was open** when its request changed (the review notice itself appears once the card is opened), and says **Note not sent**, **Change request not sent**, or **Rejection reason not sent** when the board typed a text there and did not send it.
- **What was typed is kept.** The page keeps, per request, the text of an open note, change-request, or reject panel together with the panel it was typed in. Closing the card and opening it again, `J`/`K`, the kind filter, the sort, a search, **Compact** / **Full cards**, **Show N more**, undoing another approval, a reload of the list, and a visit to the other tab all bring the card back with the same panel open and the same text. A rejection reason or a change request never comes back as an approval note. The text is forgotten when the decision lands, when the reader presses **Cancel** or **Remove note**, and when the page is left.
- **One card open at a time.** On load the first card is open. That choice is made once, when the list has loaded: a reload that puts another request first (a resubmitted older request, a new one under **Newest first**) does not open that request in place of the one being read. The page usually opens with a copy of the list that the sidebar already loaded, while a fresh copy is on its way. The first card of that copy is shown open, and it is pinned as soon as the reader puts focus in the list (a click into a field, `Tab`, `J`/`K`), also before the fresh copy arrives. If the reader has not been in the list and the fresh copy has another first card, that card opens instead, and because the page opened it and not the reader, **Approve** on it waits 0.8 seconds as after a decision (see "A double click" below). When the reader presses a kind filter or **Sort** before the fresh copy arrives, the first card is the one their own press put there, and **Approve** on it does not wait. Opening a card closes the one that was open, and pressing an open card's header closes it. A card the reader opens by its header is scrolled into view: when the card that closes sat above it, the list moves up by that card's height, and the opened card would otherwise lie above the visible area. When its top is still above the visible area after that (a card taller than the screen), its top is shown, not its end. The open card carries a ring, because it is the card the shortcuts act on. When the open card's request leaves the list, no card is open; if that request returns later, it returns as a closed row.
- **`J` and `K`** move focus to the next or previous row and open it (a compact decided or held row has nothing to open). The row is scrolled into view, and a request taller than the window is shown from its top, not its end, as when it is opened by its header. The page remembers the row that last held focus: when focus is on the page or outside the list, `J` and `K` continue from that row instead of from the top. They do nothing while a dialog is open, such as the keyboard-shortcuts list; neither does `Shift+Z`.
- **Decided elsewhere.** When the request that is open, or the row that last held focus, stops being `pending` because someone else decided it (another board member, the same person in another tab or the inbox, the requester cancelling), it keeps its place as a compact row with its new status and the words **Decided elsewhere**. The change is announced once, focus that was in the card moves to the row, and no other request opens in its place. Its note is labelled **Decision note.**, not **Your note.** It is not counted as decided on this visit. The same row is shown for a request the board sent back on this visit that was then approved or rejected elsewhere, and for one the board sent back, that was resubmitted, and that someone else then sent back again: that later decision has the same status as the reader's own, so it is told apart by its later decision time, and the row shows its note, not the reader's. A decision of this page that is still on its way is never called someone else's: when the list reloads before the reader's own second send-back, or their rejection, has been answered, the row shows what the server holds without **Decided elsewhere**. A held approval whose request is approved, rejected, or cancelled elsewhere during the hold is taken back and shown this way too (see **Taken back when the request is decided elsewhere** below), and so is one that is undone after a reload showed its request no longer pending and before the page drew it (see **Undo** below). Under **All decisions** such a row keeps its place until the tab is changed. Any other request that is decided elsewhere leaves the list as before.
- **After a decision** (for an approval: as soon as it is held, before it is sent) the card becomes its compact row and the next undecided request after it opens; when none follows, the nearest undecided request before it; when none is left, nothing. If focus was inside the decided card or on the page, focus moves to the newly opened card (or, with nothing left to open, to the decided row), so it never drops to the page. The opened card is scrolled into view, and when the decided card began above the visible area its row is brought to the top first, so the reader is not left looking past the next request. If the reader had already put focus somewhere else, or opened another card while the decision was on its way, nothing is moved. Compact decided rows can always take focus. When showing the next card would push the decided row above the visible area, that row is brought back to the top with the next card under it, so a held approval's **Undo** stays in view; rows scrolled to the top clear the bar a phone keeps at the top of the screen. With two or three holds running at once, the rows of the earlier ones are kept in view as well: the first held row that is still counting down, among those close above the row just decided (within half a window of its end), is the one brought to the top, with the other rows and the next card under it. When the next card is too tall to fit under them, it is the end of that card that is out of view, not an **Undo**. A hold started far up the list is not scrolled back to, because the card just opened would then be the one out of view; `Shift+Z` still reaches it.
- **A double click does not approve another request.** The card the page opens by itself after a decision can put its **Approve** button where the last one was pressed, and in the **Full cards** view every card below the decided one moves up, so the **Approve** of the next card, or of the one after it, can come to rest under the pointer. For 0.8 seconds after such a move (`APPROVE_AFTER_ADVANCE_MS`), **Approve** and `Shift+A` do nothing, on whichever card they land: no hold starts and no card is marked busy. The press is ignored without a message, and the same press works once the moment has passed. The same moment starts when the reader opens a row by its header (a click, a tap, or `Enter` on it): the card above closes, the row opens where its header was, and its **Approve** can lie under the pointer, so the second press of a double click or double tap on a row would otherwise approve a request nobody has read. The moment ends at once when the reader moves with `J`/`K` and when they undo a hold. The rule is keyed on the move, not on the decision before it, so it also follows **Reject request** or **Send request**, whose move comes when the decision lands. Its cost: a deliberate **Approve** less than 0.8 seconds after the page moved on (in the **Full cards** view, on another card), or after the reader opened the row by its header, is ignored the same way. Apart from that, on every surface the **Approve** button takes only the first click of a double click: the browser numbers the clicks of one (`detail` 2 and more, also when the first click was on another element such as the row's header), and the later ones do nothing. A press by the keyboard and `Shift+A` carry no such number and are not affected. A second, separate click on the same spot later than both limits still lands on **Approve**.
- **The approval's own page waits a moment too.** On `/approvals/<id>` a pointer press on **Approve** is ignored for the first 0.8 seconds after the decision controls are drawn. The press that opened the page (a row title in the Inbox, **View details** in the queue) can be followed by a second, slower press at the same point, and **Approve** may now be there; that page sends at once, with no undo. A press by the keyboard is taken at once.
- **An inbox row waits a moment too.** The inbox is a live list, newest first, and its **Approve** sends at once, with no undo. A request that arrives while the pointer rests on one row's **Approve** pushes every row below it down, and the **Approve** of another request, or of the new one, comes to rest under the pointer. A pointer press on a row's **Approve** is therefore ignored for 0.8 seconds after its buttons are drawn, and for 0.8 seconds after the list gave the row another place: a new item above it, an item above it gone, a re-sort. The press is ignored without a message, and the same press works once the moment has passed. A row whose place did not change takes the press at once, and a press by the keyboard is always taken. The rule follows the row's place in the list, not its position on the screen: a row above that only gets taller or shorter does not start it. Its cost: collapsing a group, a search, or archiving a row above moves rows as well, and a deliberate **Approve** less than 0.8 seconds later is ignored. The plain **Approve** / **Reject** pair of a type without a summary, which no request has today, is not covered.
- **Paging.** The page shows up to 20 cards, and compact rows (decided, held, or being sent) do not count against that number. Each decision therefore brings the next request onto the page, so a full page of undecided requests stays in view for as long as more exist. A card that returns after an undo or a failed approval is added to the page; no request leaves the page to make room for it. A held approval, a request whose decision failed, and the open card stay on the page even when the kind filter, the sort, or a search term would put them past its end or leave them out. **Show N more** adds another 20 and moves focus to the first request it brings in.
- **Progress.** Once a request has been decided on this visit, **N decided this visit · M left to decide** is shown beside the sort control. Requests sent back for changes count as decided, and so does an approval that is held; undoing it takes it out of the count again.
- **Compact / Full cards.** Two buttons switch **To decide** between the compact rows and cards that are always open, as before. The choice is kept in the browser (`localStorage` key `paperclip.approvals.view`) and defaults to compact. In the full view every card is open and has no header button; with shortcuts enabled the card that holds focus is marked. While a search term is set, the full view shows closed rows like the compact view. Focus, scrolling, paging, and progress work the same in both views.
- **All decisions.** Every card starts closed, in both views, and any card can be opened to read it. A closed row of a decided request shows when it was decided. The tab reads by the time of the last decision, latest first: `decidedAt` for a request that is approved, rejected, cancelled, or sent back, and the creation time for a pending request, which has no decision. A request filed weeks ago and decided a minute ago is therefore at the top, not past the end of the page. A pending request listed there can be decided only after it is opened. After a decision in this tab the reader stays on the decided row; the page does not jump to the next undecided request further down the history. That row also keeps its place: a request decided in this tab on this visit stays where its creation time put it until the tab is changed, and so does one whose approval is held, on its way, or failed. On the next visit to the tab it is placed by its decision time. A request that someone else decides while the tab is open is not held in place: it moves to its new position when the list reloads.
- **Links to one request.** `/approvals/pending#approval-<id>` (or `/approvals/all#approval-<id>`) opens that card on load, pages far enough to show it, and moves focus to it. The address may carry a kind filter and a sort as well (`/approvals/pending?kind=email_reply&sort=newest#approval-<id>`); a request the filter leaves out counts as not listed. A link to a request in **Waiting on the requester** unfolds that section, scrolls its row to the top, and moves focus to the row. A link to a request the tab does not list opens no card (so no other request stands open in its place) and announces **The linked request is not in this list. Its status is _status_.**, or **The linked request was not found.** The same link works again after the reader has been somewhere else.
- **Sort and kind filter.** Choosing a kind or reversing the order starts the list like a fresh one, with its first card open. Both are kept in the address as a query string: `?kind=<kind>` (`email_reply`, `request_board_approval`, `hire_agent`, `approve_ceo_strategy`, `budget_override_required`) and `?sort=oldest` or `?sort=newest`. A value that is the default is left out, and a value the page does not know is ignored. A kind the tab does not list (no request of that kind is in it, for example after the last email reply was decided) is removed from the address once the list has loaded, in place, with the rest of the query, the `#approval-<id>` target, and the navigation state kept: left there, a later reload that brings a request of that kind would narrow the queue by itself. A reload, a bookmark, and the way back from **View details** therefore show the same view. The address is changed in place: no history entry is added, the page stays the same page, and a `#approval-<id>` target is dropped, because the list starts afresh. Nothing held is sent, and what was typed and which revisions were confirmed are kept. A change of tab returns the kind to **All** and the order to its default (oldest first under **To decide**, latest decision first under **All decisions**), because the tab links carry no query. The view switch (**Compact** / **Full cards**) is not in the address; it is kept in the browser.
- **Kind counts.** Each kind chip, and **All**, shows a number. Under **To decide** it is the number of undecided requests of that kind: still `pending`, and not decided or held on this visit. A held approval is not counted; undoing it brings the request back into the number. Under **All decisions** it is the number of requests of that kind the tab lists. A search term narrows the numbers as it narrows the list. A row that is only kept on the page (a held approval, a failed request, or the open card, of another kind or without the term) is not added to a number. The chips, and so the numbers, are shown only when the tab lists more than one kind.
- **Search.** A field above the list narrows it to the requests that hold the typed term, whatever the case, in the subject as the card shows it, in the requester's name (from the company's agent list), in the payload's `summary`, or in the recommendation. The rationale, the draft reply, the original request, and linked tasks are not searched. Beside the field the page says how many requests of the tab and the chosen kind hold the term (**3 found**, **None found**), as a polite status. While a term is set the results are closed rows, in both views, and no card is opened by the page: a held approval, a request whose decision failed, a **Decided elsewhere** row, and a card that an undo brings back stay listed whatever the term, and nothing is decided from a closed row. A row the reader opens is decided as usual, and the next result opens after the decision. While a term is set, changing the term, the kind, or the order closes the open card; what was typed in the card is kept. A new term starts the page size again, as a new kind does. Emptying the field brings the whole list back with its first card open; the page opens that card, possibly under a pointer resting on a result, so **Approve** on it waits 0.8 seconds as after a decision (a kind or **Sort** press does not start that wait). The field stays on the page for as long as it holds text, also when the tab lists nothing any more, so the term can be read and cleared. Typing a term sends nothing early. The term is not part of the address and is emptied by a change of tab or company. With keyboard shortcuts enabled, the app's `/` key puts focus in the field; `J`, `K`, and `Shift+Z` do nothing while focus is in it; `Enter`, or `Escape` in an empty field, leaves it. The inbox search finds an approval by its label and type as before, and also by its requester's name and its recommendation.

Approval cards on a task page and in a comment thread are not collapsible; they are always open.

### The undo window after Approve

The server acts on an approval in the request that stores it: it activates a hire, writes the activity log, and wakes the requesting agent. There is no route that reverses a decision. The Approvals page therefore holds every approval in the browser for five seconds (`APPROVE_HOLD_MS`) before it sends it. This is the only moment at which an approval can be taken back. The inbox, the detail page, and task pages do not hold; they send at once. **Reject** and **Request changes** are not held anywhere: one asks for confirmation and the other requires a note.

- **Held.** Pressing **Approve** (or `Shift+A`) turns the card into a compact row at once: **Approving in 5s**, counting down each second, the title, the note under **Your note.** when one was typed (with its line breaks), and an **Undo** button. Nothing has been sent. The reader is moved on exactly as after any decision: the next undecided request opens and takes focus, and the held approval counts as decided in the progress line.
- **Undo.** **Undo**, or `Shift+Z` for the most recent hold when keyboard shortcuts are enabled, cancels the approval. Nothing is sent. The full card returns in its place, open and in focus, with the typed note in an open note panel. `Shift+Z` is ignored in a text field, with another modifier key, and while the key is held down. When the loaded list shows that the request stopped being `pending` during the hold, in a reload the page has not drawn yet (once it is drawn, the page takes the hold back by itself, see below), there is no card to return to: nothing is sent, the request keeps its place as a compact row with its real status and **Decided elsewhere**, focus goes to that row, and the card the reader is at stays open with what they typed. The note typed with the approval is kept and returns with the card if the request is resubmitted.
- **Paused while the reader is at Undo, for thirty seconds at most.** The five seconds do not run out once a mouse or pen pointer has moved over the held row, or while keyboard focus is on its **Undo** button. The row then reads **Paused, _N_s left**, and the button tells a screen reader that the approval is not sent while it has focus, for up to 30 seconds in all. When the pointer leaves and focus moves on, the rest of the time runs. Only a movement of the pointer over the row pauses: a held row that is drawn or scrolled under a pointer lying still does not (the browser reports the pointer as entering the row then, although the reader did nothing), so a mouse parked over the list does not keep a keyboard reader's approvals unsent. A touch does not pause. A hold stands still for 30 seconds at most (`APPROVE_PAUSE_LIMIT_MS`), counted over all its pauses and both reasons together. After that the countdown runs whatever the pointer or focus does and cannot be paused again; the row reads **Pause over, sending in _N_s**, the **Undo** button's description says the same, and the live region says it once. A hold whose pause is ended by the limit then runs for at least 3 seconds (`APPROVE_AFTER_PAUSE_LIMIT_MS`, and never longer than the hold itself), however little it had left when it was paused, so that the notice can be read and heard and **Undo** still reached; a hold paused in its last moment is not sent in the moment the limit is reached. **Undo** works until the approval is sent. A paused approval is still sent at once in every case listed under "Never dropped, never sent twice" below, and is still cancelled by **Undo**.
- **Sent.** When the five seconds are up the approval is sent with its note. The row reads **Approving...** and has no **Undo**; an approval that has been sent cannot be taken back. When it lands, the same row becomes the normal decided row. Focus resting on the row, or on its **Undo** button, stays on the row throughout.
- **Failed.** If the request comes back as an error, its card returns with the error and the typed note. By then the reader has usually moved on, so the page does not take them back: when another request is open, when focus is in another row, or when the cursor is in a text field, nothing is opened or closed and focus is not moved. The error shows on the failed request's closed row, with **Note not sent** when a note was typed, and the note is back when the card is opened. A toast reports the failure as well only when that row is out of view (above the visible part of the list, or below the window). Its **View request** action stays on the queue while the queue still shows the request: it scrolls to the row and moves focus there, and opens, holds, and sends nothing. On a phone the toast lies over the open request's **Approve** button, and a tap meant for that button must not leave the queue, which would send every other hold at once. When the row is in view no toast is raised: the toast comes up in the bottom-left corner, where the open request's **Approve** button rests, and would cover it for 15 seconds. Only when the reader is at no other request (nothing else is open and focus is on the page or on the failed row) does the card return open, scrolled into view, and in focus; focus on a control outside the list stays there. As with any decision, an error does not prove the approval was not stored, so the list is reloaded.
- **Never dropped, never sent twice.** A held approval is sent at once, without waiting for its time, when the reader leaves the page, changes tab (**To decide** / **All decisions**) or company, when the browser tab is hidden (`visibilitychange` to `hidden`), and on `pagehide`. Each hold is sent exactly once, whichever of these comes first. Changing the kind filter or the sort, or typing a search term, does not send it; the hold keeps running, and its row with **Undo** stays listed whatever the filter, the order, and the term. If the browser ends the page without any of these events (a crash), the approval is not sent and the request stays pending. Apart from **Undo**, two things keep a held approval from being sent: a revision of its request, and its request being sent back for changes, described next.
- **Taken back when the request is revised.** An approval is held for the version the reader pressed **Approve** on. If the list reloads during the hold (most likely while it is paused) and shows that the requester has resubmitted the request with another payload, the hold is cancelled and nothing is sent. The card returns in its place as a closed row marked **Revised while this page was open**, with **Note not sent** when a note was typed, and with the line **Not approved. The requester revised this request before your approval was sent.** where a failed decision is shown. Like a request whose decision failed, it stays on the page whatever the kind filter and the page size, and the line stays until the reader approves again, edits the note, or changes tab. The page also says so in its live region and, when the row is out of view, in a toast (**Not approved: _title_**); a row in view says it itself, and the toast would cover the open request's **Approve** button. **Approve** on the returned card waits for **I have reviewed it** like any other revision. Focus that rested on the held row or its **Undo** moves to the returned row. A reload that only shows a newer time with the same payload changes nothing, and an approval that is already on its way cannot be taken back.
- **Taken back when the request is sent back.** The same happens as soon as a reload shows the request sent back for changes (`revision_requested`) by someone else during the hold, before any resubmission. The server would still store the approval, over that board member's change request, and a paused hold can stand for up to thirty seconds. The hold is cancelled and nothing is sent. The request stays in its place as a closed card with its real status, without decision buttons (**Waiting on the requester to revise**, with the colleague's note once opened), and with the line **Not approved. This request was sent back for changes before your approval was sent.** The live region says so, and a toast when the row is out of view. When the reader had sent this request back earlier on this visit, the request is drawn as a **Decided elsewhere** row instead (see above), which has no place for that line: the toast is then raised whether or not the row is in view. Focus that rested on the held row or its **Undo** moves to the returned row. The line stays until the reader changes tab, or approves again once the request has been resubmitted. The note typed with the approval is kept for when the request returns.
- **Taken back when the request is decided elsewhere.** The same happens as soon as a reload shows the request approved, rejected, or cancelled by someone else during the hold (another board member, the same person in another tab or the inbox, the requester cancelling). Sent all the same, an approval of an approved request would be answered as if it were this reader's decision, with the other person's note shown as **Your note.**, and an approval of a rejected or cancelled request would come back as an error on a card that no longer has anything to decide. The hold is cancelled and nothing is sent. There is no card to return to: the request keeps its place as a compact row with its real status, **Decided elsewhere**, and the other decision's note as **Decision note.** That row stays listed under any kind and search term until the tab is changed, so a held row never just disappears. It is not counted as decided on this visit, and the request being read stays open. The live region says **Not approved: _title_. Nothing was sent. Its status is now _status_: decided elsewhere.** once, and a toast says so (**Not approved: _title_**) only when the row is out of view. Focus that rested on the held row or its **Undo** moves to the row. The note typed with the approval is kept as a draft. One case is the reader's own: an approval that was sent on this visit and came back as an error may have been stored all the same. When the reader approves again and a reload then shows the request approved, the second hold is cancelled, nothing is sent twice, and the row is the reader's own decision: no **Decided elsewhere**, counted as decided on this visit, announced as **Approved: _title_**. The page cannot tell this from someone else approving in the moment between the failed send and the reload. The list correction the page writes for its own approval that has landed, and an approval of its own that is already on its way, take no hold back. These three are the only cases in which a held approval is not sent without the reader pressing **Undo**.
- **A limit that remains.** All three take-backs act on a reload of the list that has arrived and been drawn. A send-back, a revision, or another decision whose reload has not arrived when the hold ends is not seen in time, and the approval is sent; so is a hold that is sent at once because the page is left, hidden, or changed to another tab or company, which has no reloaded list to consult: in a test against a local server, a request resubmitted with another payload in the last half second or so of a hold was approved in its revised form. The page does not read the request once more before it sends. That read would narrow the gap to one round trip, not close it, and the same send path serves a page that is being left, where waiting for a read could leave the approval unsent. Closing the gap needs the server to check which version an approval was given for; the approve route has no such check, and this interface does not add one.
- **Outliving the page.** Every held approval is sent with `fetch`'s `keepalive` option, so the request reaches the server even when the tab is closed or navigated away immediately afterwards.
- **A failure the page cannot show.** If a held approval fails after the reader has left the page, or when its row is not on the page (another company, a list that no longer holds the request), the error is shown as a toast whose **View request** action opens the request's own page (`/approvals/<id>`). Which of the two the action does is decided when it is pressed, not when the toast is raised: the reader may change tab or company, or leave the queue, while the toast is up. A toast raised before the reader left the queue and came back opens the request's own page.
- **Several at once.** Each approval has its own five seconds; the reader can keep going down the queue while earlier ones count down.
- **The returned note.** The note that comes back with a card is the one typed with the approval. It is kept like any other text the board typed and did not send (see "What was typed is kept" above): edits are kept too, and **Remove note** forgets it.

Another board member can still decide the same request while it is held. When a reload shows the page that they approved, rejected, or sent it back, or that it was cancelled, the hold is taken back as described above and nothing is sent. Only if that reload has not reached the page when the hold ends is the approval sent, and the server answers as it would for any late decision: an approval of a request that was rejected or cancelled in the meantime comes back as an error on the card; an approval of one that was approved in the meantime changes nothing and wakes nobody a second time; an approval of one that was sent back is stored for the version the reader read.

When any decision lands, the page writes the decided record into the loaded approvals list at once and then reloads the list. Both are done for the list of the company the request belongs to, which the decision carries with it: a rejection or change request that lands after the reader has changed company still corrects that company's list, so the request is not offered again on their return. The rows decided on a visit are forgotten on a change of tab, and without this a list that had not reloaded yet would show the request under **To decide** again, with **Approve** ready for a second approval.

### Requests sent back for changes

**Request changes** sets the approval to `revision_requested` and stores the board's note as its `decisionNote`. The requester has the request from then on: it returns to `pending` only when it is resubmitted, and a resubmission may replace the payload and clears the note. The server still accepts **Approve** and **Reject** for a `revision_requested` approval, so the interface decides where those are offered:

- **To decide** on the Approvals page lists only `pending` approvals, and its badge counts only those. The count on the tab is drawn like the sidebar's: dark on light in the light theme, light on dark in the dark theme. A request decided or sent back during the visit keeps its place as a compact row, as before. When a request sent back during the visit is resubmitted, its card returns in the same place. Once opened, that card shows the reader's change request above the summary, under **Changes you asked for**, as plain text with its line breaks, so the revision can be read against it. The server deleted the note with the resubmission; the page shows the copy it kept from the reader's own decision. It is shown until the request is decided again or the tab is changed. On a later visit it is gone, and so is a change request sent from another page: only the server can keep those.
- Below the queue, **Waiting on the requester (N)** lists the other `revision_requested` approvals. The section is folded away until its button is pressed, and it is not shown when there are none. Each row shows the status, the subject, **Sent back _time ago_** (from `decidedAt`, or from `updatedAt` when no decision time is recorded), the note under **Changes you asked for**, and **View details**. The rows carry no decision buttons, are not part of `J`/`K`, and are not affected by the kind filter, the sort, or the search. They are listed longest-waiting first.
- The approval card (Approvals page, task page, **All decisions**) and the inbox row, in both inbox presentations, offer no decision for a `revision_requested` approval: no buttons, no note field, and no `Shift+A`, `Shift+C`, or `Shift+X`. In their place stands **Waiting on _requester name_ to revise** (**Waiting on the requester to revise** when the name is not known), **Sent back _time ago_**, and the note under **Changes you asked for**. The card does not show a **Waiting N days** clock for it. **View details** stays.
- The approval detail page keeps **Approve** and **Reject** for a `revision_requested` approval, and labels the note **Changes you asked for**. It is the one place where the version the board asked to change can still be decided, with the whole request on the page. **Mark resubmitted**, which the page offers for such a request, asks for confirmation first, as **Delete disapproved agent** does. The question says what the press does: the request returns to the queue unchanged, the change request is deleted, and the requester can no longer resubmit a revised version. Declining sends nothing.
- The board's own note is shown as it was typed, on every surface: the change request and the decision note keep their line breaks (a numbered list of changes stays a list) and a long unbroken run wraps. This holds for **Changes you asked for** and **Decision note** on the detail page, **Decision note.** on the card, and **Your note.** / **Decision note.** in a compact row. A note is plain text and is never rendered as Markdown.
- The inbox still lists `revision_requested` approvals and counts them in its badge.

A closed approval says when it was closed: the card shows **Approved _time ago_**, **Rejected _time ago_**, or **Cancelled _time ago_** from `decidedAt`, in place of **Created _time ago_**. Without a `decidedAt` it shows the creation time. Who decided is not shown; the record holds only a user id.

### Requests that change while open

The server does not check which version of a request the board read. The interface therefore watches for a revision arriving under the reader:

- The card, the inbox row in both presentations, and the detail page remember the `updatedAt` and payload first shown for an approval. If the same approval arrives later while it is `pending`, with a newer `updatedAt` and a payload that is not the same (compared by value; key order does not count), it was revised while open. A newer `updatedAt` with the same payload raises nothing, and neither does a decision, which changes the status.
- A notice then appears above the summary: **The requester revised this request while it was open. Review it before you decide.** with the button **I have reviewed it**. The new content is already on the page. Sections the reader had expanded stay as they are, and a note being typed is kept. The notice is an alert when the revision arrives while its place is on the page. On the Approvals page a card's body is drawn again each time the card is opened: a notice that is already due then is shown without being an alert, so it is not spoken again on every opening. The closed row's header is described by **Revised while this page was open**, and **Approve** still moves focus to the notice.
- Until that button is pressed, **Approve** (a click or `Shift+A`) sends nothing. It moves focus to the notice and shows **Confirm that you have reviewed the revised request, then approve.** beside the buttons. **Reject** and **Request changes** are not held back. An inbox row with the plain **Approve** / **Reject** buttons is held back the same way.
- Pressing **I have reviewed it** makes the version on the page the remembered one and leaves a quiet line saying the request was revised and marked as reviewed. A later revision raises the notice again.
- This check comes before the check on a cut draft: the first **Approve** after a revision is held back for the revision only, and once it is confirmed a cut draft is still opened before anything is sent.
- The check is made in the browser. In the inbox and on the detail page it lasts for as long as that row or page is shown. The Approvals page remembers per request, for as long as the page is open, the version it first showed and the revisions the reader confirmed. A card that is closed, filtered out, paged out, or re-sorted and drawn again therefore still shows the notice until it is confirmed, and does not ask again once it was. A request that left the queue because it was sent back somewhere else (another board member, the inbox, another tab) and returns resubmitted with another payload comes back as a closed row marked **Revised while this page was open**, and **Approve** waits for the confirmation. The one exception is a request the board sent back from this page: its revision is what the board asked for, so its card returns closed, to be opened and read, without the notice. An approval that is still held when its request is revised is not sent: see "Taken back when the request is revised" under "The undo window after Approve".

The detail page follows live updates: an approval event reloads that approval, its discussion, and its linked tasks as well as the list, so a resubmission, another member's decision, or a new comment appears without a reload of the page.

Approval cards on a task page follow them too. An approval event names the approval, not its tasks, so it reloads the linked approvals of every task page that is open (the `["issues", "approvals"]` query keys). A card there no longer keeps showing the version the board read after the requester has resubmitted another one, and the check described above sees the revision.
